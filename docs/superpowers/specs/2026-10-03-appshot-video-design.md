# appshot video: `record` and `compose video`

Status: design approved in conversation 2026-10-03, awaiting spec review.

## Goal

Produce short app videos for every app in the fleet the same way appshot produces
screenshots: staged, deterministic, regenerated by a command, and reviewable by an
agent that cannot watch a video.

One recording yields two kinds of output:

- **App Store app previews**, held to Apple's specification.
- **Promos** for X ads, social posts and the marketing sites: framed on the
  theme gradient, captioned, with an end card.

The first consumer is Armada, whose X ad is waiting on a video. Armada does not
ship on the App Store, so it needs promos only.

### Success criteria

- `appshot record` + `appshot compose video` turn a config entry into a
  1080x1080 Armada promo with no hand editing.
- An App Store preview from the same recording passes Apple's checks:
  size, 15-30 s, 30 fps, H.264, stereo audio track.
- Re-running the pipeline on an unchanged app produces keyframes that pass
  `appshot check` against the goldens.
- Changing a caption or its timing needs a render only, never a re-record.
- No synthetic input reaches the machine at any point: nothing clicks, types or
  moves the real pointer.

### Out of scope

Music and voiceover, App Store Connect preview upload through the MCP, localized
captions, vertical 9:16 promos.

## Apple's constraints (checked 2026-10-03)

From the App Store Connect app preview specifications and the App Store app
preview guidelines:

| | |
|---|---|
| Length | 15-30 s |
| Frame rate | 30 fps max |
| Video | H.264 High Profile up to Level 4.0, 10-12 Mbps VBR (or ProRes 422 HQ) |
| Container | .mov, .m4v, .mp4 |
| Audio | stereo, 256 kbps AAC, 44.1 or 48 kHz; all tracks enabled |
| macOS size | 1920x1080, landscape only |
| iPhone 6.9"/6.5"/6.1" | 886x1920 or 1920x886 |
| iPad 13"/11" | 1200x1600 or 1600x1200 |
| Count | up to 3 per localization |
| Poster frame | defaults to 5 s |

Content: only footage from within the app. No people, hands or over-the-shoulder
shots. Text overlays are encouraged and must stay on screen long enough to read.
Graphic elements such as touch hotspots may show how interaction works. No
prices, no seasonal references.

## 1. Contract between appshot and the app

appshot owns the timeline. The app owns named actions.

### Config

Videos live in the existing `screenshots.config.json`, beside `screens[]`, so
copy and pacing change without touching code:

```json
"videos": [{
  "id": "armada-intro",
  "stage": "menubar",
  "duration": 24,
  "poster": 5,
  "outputs": {
    "preview": false,
    "promo": [[1920, 1080], [1080, 1080]],
    "website": true
  },
  "beats": [
    { "at": 0.0,  "caption": "5 Claude Code sessions.\nWhich one needs you?" },
    { "at": 1.5,  "cue": "session.waiting", "args": { "row": 2 } },
    { "at": 3.0,  "cue": "pointer.click",   "args": { "target": "row-2" } },
    { "at": 3.2,  "cue": "window.focus",    "args": { "row": 2 }, "caption": "Jump straight to it" },
    { "at": 4.0,  "zoom": { "target": "row-2", "scale": 1.6 } },
    { "at": 10.0, "cue": "stage", "args": { "to": "codex" }, "caption": "Codex and Grok Build too" },
    { "at": 17.0, "cue": "stage", "args": { "to": "history" } },
    { "at": 21.0, "endCard": true }
  ]
}]
```

`stage` is the `-ScreenshotStage` the app launches into. A beat may carry any
combination of `cue`, `caption`, `zoom` and `endCard`. A caption holds until the
next caption or its own `until`.

### Files

Both live where the ready file lives today (`Capture.readyFileURL`): inside the
app's sandbox container when it has one, `~/Library/Containers/<id>/Data/tmp` on
macOS and the app data container on a simulator. The app can read and write
there; appshot, unsandboxed, can too.

- **Cue file**, appshot to app, passed as `-ScreenshotCueFile <path>`. appshot
  appends one JSON line per cue at its scheduled time:
  `{"seq": 3, "t": 3.0, "cue": "pointer.click", "args": {"target": "row-2"}}`.
  The app watches the file and executes every line whose `seq` it has not run.
- **Event file**, app to appshot, passed as `-ScreenshotEventFile <path>`. The
  app appends JSON lines:
  - `{"kind": "ready"}` once the stage has rendered;
  - `{"kind": "ack", "seq": 3}` after a cue's effect is committed (one runloop
    turn after the change, as the ready file does today);
  - `{"kind": "target", "seq": 3, "name": "row-2", "rect": [x, y, w, h]}` in
    screen points, answering a pointer or zoom cue;
  - `{"kind": "unknown", "seq": 3, "cue": "..."}` for a cue it does not
    implement.

The still-capture ready file is unchanged; `capture` keeps working against apps
that never learn about video.

### Shared cue vocabulary

Documented by appshot, implemented by each app in its `#if DEBUG` demo seed:

| Cue | Args | Meaning |
|---|---|---|
| `stage` | `to` | switch to another `-ScreenshotStage` value without relaunching |
| `pointer.move` | `target` | report `target`'s rect; nothing else changes |
| `pointer.click` | `target` | report `target`'s rect, then perform the click's effect in-app |
| `scroll` | `target`, `to` | scroll a named container to a named element |

Anything app-specific is namespaced by the app's own words (`session.waiting`).

### Failure rules

- An `unknown` event, a cue with no `ack` within 1 s, or no `ready` within
  `settleMax` fails the run. A cue that silently does nothing must never pass.
- Cue latency (ack time minus scheduled time) above 50 ms is reported; above
  250 ms it fails the run.

## 2. Recording: `appshot record`

```
appshot record --app build/Armada.app --config ... --videos armada-intro \
  --appearances dark [--no-activate]
```

### macOS

- ScreenCaptureKit `SCStream` with a content filter of the app's windows, matched
  by pid exactly as `capture` matches them, re-evaluated as windows appear so a
  window opened mid-run joins the recording. Real cursor hidden
  (`showsCursor = false`); appshot draws its own.
- 60 fps at backing scale, written as **HEVC with alpha** (hardware encoded) so
  rounded corners survive into compositing, as they do in the PNGs.
  The system shadow is deliberately excluded (it bled into the corners, measured alpha 6);
  compose draws its own.
- The stage rect is the union of every app window frame reported over the run,
  fixed before rendering so the frame never wanders.
- With `--no-activate` and no synthetic input, the person may be able to keep
  working during a take. This depends on spike result 1.

### iOS

- `xcrun simctl io <udid> recordVideo --codec=h264` on the dedicated simulator
  appshot already creates, with the status bar override already in place.
- appshot waits for the first frame to land, takes that as t = 0, and only then
  sends the first cue. Lead-in before t = 0 is trimmed at render.

### Output

```
videos/source/<id>~<appearance>.mov         master
videos/source/<id>~<appearance>.track.json  what actually happened
```

The track holds every beat with its scheduled and actual time, every event from
the app, the window frames over time, and dropped-frame counts. Rendering reads
the track, never the plan, so a late cue moves its caption with it.

## 3. Rendering: `appshot compose video`

A pure function of master + track + config, built on AVFoundation
(`AVAssetReader` / `AVAssetWriter`) with Core Image compositing and appshot's
existing gradient and CoreText code. Re-rendering after a copy change takes
seconds.

### Outputs

| | `preview` | `promo` |
|---|---|---|
| Size | Apple's sizes only, by platform | from `outputs.promo` |
| Surround | solid, the theme gradient's darkest stop. Apps may pin a 16:9 window for video so the border nearly vanishes | the theme gradient |
| Captions | small strip along the bottom | large title above the window, stills layout |
| End card | none | icon, name, URL |
| Encoding | H.264 High 4.0 ~10 Mbps, 30 fps, silent stereo AAC 48 kHz | H.264, 30 fps, silent stereo AAC |
| Enforced | 15-30 s, 30 fps, exact size, `poster` time | none beyond shared checks |

```
videos/preview/<id>~<appearance>.mp4
videos/promo/<id>~<appearance>~<w>x<h>.mp4
videos/promo/<id>~<appearance>.poster.png
<website>/src/assets/videos/<id>.mp4         when outputs.website is true
```

appshot owns the website videos directory the way it owns
`src/assets/screenshots/`.

### Overlays

- **Cursor** (macOS): a plain arrow drawn by appshot, not Apple's artwork. It
  eases between reported targets; a click adds a small ring ripple.
- **Touch** (iOS): a translucent circle at the target, the "touch hotspot" the
  guidelines allow.
- **Zoom**: eases the virtual camera toward a reported target. Needed for
  promos, where a full Mac window at 1080 px wide is unreadable in a phone feed.
- **Captions**: fade 0.25 s in and out. **Reading-time check**: a caption on
  screen for less than 1 s + 0.3 s per word fails the render.

### From stills: `compose video --from-stills`

Builds a stand-in master from existing `source/<id>~<appearance>.png` captures:
each beat names a screen instead of a cue, with crossfades between them, and the
same captions, zoom and end card on top. Any fleet app can produce a promo
before it implements a single cue, and the ad does not depend on the riskiest
part of recording.

## 4. Agent loop, gate, skill

### Review without watching

`record` and `compose video` each write:

- `<id>.report.json`: per beat, scheduled vs actual time and cue latency;
  unknown cues; unresolved targets; dropped frames; each caption's margin over
  the reading check; duration against Apple's limits.
- `<id>.contact.png`: one frame per beat taken about 0.8 s after it, plus one
  mid-caption, each labeled with its time and caption, from the actual render.

The loop: edit the scenario, `record`, read the report, `compose video`, look at
the contact sheet, then fix the copy (re-render), a cue (re-record), or a cue
handler (rebuild, re-record).

### Gate: `appshot check` for videos

- Beat keyframes from the master are gated as stills against
  `videos/golden/<id>~<appearance>@<beat>.png`, with the existing tolerance.
- **Dead cue**: two consecutive keyframes identical where the beat should have
  changed the screen. The video counterpart of the duplicates check.
- Structural: every cue acked, none unknown, latency and dropped frames within
  bounds, duration within limits.
- Known blind spot, inherited from stills: a small deliberate UI change passes
  the tolerance. The gate proves the video still plays correctly, not that it
  is current.

### Repository layout

- Committed: config, golden keyframes (LFS, like the PNG goldens), website mp4
  (LFS: the site deploy rebuilds from the repo).
- Git-ignored: masters, previews, promos.
- Preview upload is manual until App Store Connect MCP grows an app preview
  tool.

### Skill and Makefiles

- `skills/appshot-screenshot-pipeline/references/video.md`: scenario authoring,
  the cue vocabulary, a Swift recipe for the cue handler (cue file watcher,
  event file writer, `ack` after commit), the review loop, Apple's limits. The
  skill description gains "app preview", "promo video", "demo video".
- Makefile targets `videos`, `videos-record`, `videos-compose`, `videos-check`
  beside `screenshots-*`, in the canonical section owned by
  `fleet-apple-conventions`.

### Testing appshot itself

- `AppShotFixture` learns the cue and event files. An integration test records
  3 s and asserts the track, alpha survival and cue latency.
- Render unit tests feed a synthetic master of generated frames: caption
  placement, zoom easing, cursor path, reading check, Apple limits. No
  recording needed.

## 5. Rollout

| Phase | Work | Result |
|---|---|---|
| 0. Spike (~2 h, throwaway) | (1) SCStream filtered to one app's windows keeps alpha and survives occlusion by another app. (2) HEVC-with-alpha masters and simulator H.264 decode in AVFoundation. (3) `simctl recordVideo` first-frame sync | go / no-go on section 2 |
| 1. appshot core | cue and event files, fixture, macOS `record`, `compose video` both outputs, report, contact sheet | appshot 0.20.0 |
| 1b. From stills | `compose video --from-stills` | every app can make a promo with no cue code |
| 2. Armada | `DemoSeed` cue handler (`stage`, `pointer.*`, `session.waiting`), first scenario, 1080x1080 and 16:9 promos | the X ad |
| 3. Gate and fleet | video `check`, Makefile targets, `video.md`, the fleet-apple-conventions section | videos that stay correct |
| 4. iOS | simulator `record`, touch hotspots, iPhone and iPad preview sizes | first iOS app preview |
| 5. Fleet | bastion and cupertino (promo), then App Store apps (preview + promo), by install count | each app costs a cue handler and a scenario |

If the spike fails on recording, 1b still delivers the Armada promo from the
existing screenshots.

## Spike results (2026-10-03)

1. SCStream filtered to the app's windows (`SCContentFilter(display:including:)`),
   HEVC with alpha in a .mov: writer status 2 (completed), 235 frames over 4.13 s
   (60 fps requested), 3456x2234 (display pixels, scale 2), 841 KB. Occlusion: a
   second window (opaque magenta, `.floating`, `orderFrontRegardless`, created by
   the script itself at ~2 s, covering the probed point; no human input) did not
   appear in the recording. The fixture pixels under it, probed at frames 100 (just
   before) and 170 and 220 (after), are identical to the unoccluded frames:
   BGRA(221,222,221,253) at the window center. The occluding window was
   reported visible by AppKit but was not independently confirmed on screen.
2. AVFoundation readback (BGRA, `AVAssetReaderTrackOutput`): corner alpha 0 at
   display pixel (2,2), center alpha 253 (not 255; HEVC alpha is lossy, and the
   inset probe in the title area also reads 253), all 235 frames decode.
   Gates on alpha must therefore use a threshold (e.g. >= 250), not equality.
   Track is hvc1, yuv420p.
3. simctl recordVideo first bytes after: not run: no booted simulator;
   informational for phase 4.

Verdict: go on section 2. The window-filtered stream gives transparent
surroundings and keeps the fixture's content when another window covers it.
Caveats: use an alpha threshold, and the occlusion test used a same-process
overlay rather than another app's window.
